# Architecture Review: obsidian-summairize

The plugin is ~730 lines of TypeScript across 10 source files. The module
structure (services, utils, ui, settings, types) is reasonable for this size.
The problems below are ordered from most to least severe.

---

## 1. Command Injection via Unsanitized Model Name (Critical)

`OllamaProvider.ts:27` builds a shell command by interpolating the model name
directly:

```typescript
const command = `echo ${escapedPrompt} | ollama run ${model}`;
```

The prompt is escaped, but `model` — which comes from user-editable settings —
is not. The same issue exists at `OllamaProvider.ts:154`:

```typescript
const command = `ollama pull ${model}`;
```

A model name like `; rm -rf /` would execute arbitrary commands.
`ShellExecutor.escapeShellArg()` exists but is only used on the prompt, not the
model name. `checkCommand()` in `ShellExecutor.ts:51-54` also passes its
argument unescaped to `which`/`command -v`/`type`.

## 2. Duplicated Exclusion Logic (Design Flaw)

`main.ts:102-128` (`getExclusionReason`) reimplements the same
template/daily-note checks that `FileFilter.ts` already performs. The two copies
can drift out of sync. `FileFilter` should return the reason, not just a
boolean, eliminating the duplication entirely.

## 3. Settings Object Passed by Reference, Mutated in Multiple Places

`AIService`, `FileFilter`, and `SettingsManager` all hold references to the same
`SummarySettings` object. `SettingsManager` maintains its own `this.settings`
copy, `plugin.settings` is assigned once at startup (`main.ts:18`), and
`updateSetting` mutates `SettingsManager`'s copy but `plugin.settings` may be
stale. The only reason this works today is that `Object.assign` during
`loadSettings` mutates in place and the settings object happens to be the same
reference — this is fragile and accidental.

## 4. No Input Validation on User-Supplied Regex

`FileFilter.ts:43` and `main.ts:117` both do:

```typescript
const pattern = new RegExp(this.settings.dailyNotesPattern);
```

No try-catch and no complexity guard. Invalid or pathological regex will throw or
cause catastrophic backtracking (ReDoS).

## 5. HTTP Fetch Has No Timeout

`OllamaProvider.ts:46` calls `fetch()` with no `AbortSignal` or timeout. If the
Ollama server hangs, the plugin blocks indefinitely. The shell fallback has a
30-second timeout, but the primary HTTP path does not.

## 6. Hardcoded Ollama URL

`http://localhost:11434` appears in three places (`OllamaProvider.ts:46`, `:75`,
`:129`). Not configurable — users running Ollama on a different host/port cannot
use the plugin without editing source code.

## 7. `AIService` Breaks the Provider Abstraction

`AIService.ts:108,115,123` cast the provider to `OllamaProvider` with
`as OllamaProvider` to call Ollama-specific methods. This defeats the purpose of
the `AIProvider` abstraction and means adding a second provider requires touching
`AIService` internals.

## 8. `insertSummary` Produces Cumulative Corruption

`NoteUtils.ts:2-29`: when a summary already exists, the method injects a new
`## Generated by AI` block plus an `# Original Article` heading inside the
existing content. Running the command twice does not replace the old summary — it
nests summaries and duplicates `# Original Article` headings.
`extractContentForSummary` only strips the first match, so the AI also starts
summarizing previous summaries.

## 9. No Tests

No test framework configured. No jest/vitest/mocha in devDependencies, no test
script in package.json. The regex logic in `NoteUtils` and `FileFilter` is
exactly the kind of code that needs unit tests. The `dev_tools/` scripts are
manual smoke tests, not automated.

## 10. Stale Dependencies

- TypeScript 4.7.4 (current is 5.x)
- `@types/node` 16 (current is 20+)
- `obsidian: "latest"` — unbounded; a major release could break the build
- `package-lock.json` is gitignored — builds are not reproducible

## 11. `innerHTML` in Settings UI

`SettingsManager.ts:161-168` and `:171` use `innerHTML` to render provider
status. Obsidian provides `createEl`/`createDiv` methods to avoid raw HTML
injection. If a provider name were ever user-supplied, this would become an XSS
vector.

## 12. Minor Issues

- **Magic numbers**: 50-char minimum, 8000-char truncation limit, 100-char
  padding — none named or explained.
- **`isAvailable()` is expensive and uncached**: Up to 5 sequential
  shell/HTTP calls on every invocation, including on settings tab open.
- **PATH manipulation**: `ShellExecutor` rebuilds PATH on every call instead of
  computing once.
- **`validateSummary` is brittle**: Strips hardcoded prefix phrases — will
  silently mangle legitimate content and miss other LLM preambles.
- **No cancellation**: No way to abort a running summary generation.

---

## Summary

The module boundaries and async flow are sound for an early-stage plugin. The
two items to fix before any release are the **command injection** vulnerability
and the **summary insertion corruption**. The settings mutation model and
duplicated exclusion logic are next-priority design issues. Everything else is
normal early-project debt.
